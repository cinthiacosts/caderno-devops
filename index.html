Git: o histórico do projeto

O Git registra versões dos arquivos. Assim, podemos acompanhar o que mudou e consultar versões anteriores do projeto.

O GitHub hospeda o repositório remoto e facilita o compartilhamento. É de lá que o Jenkins vai buscar o código.

Para lembrar init inicia, add prepara, commit registra e push envia.

Comandos do meu laboratório

git init

Inicia o repositório na pasta atual.

git status

Mostra o que mudou e o que está pronto para o commit.

git add .
git commit -m "mensagem"

Prepara os arquivos e registra uma versão.

Desafio de revisão

Criei o index.html e o style.css, mas ainda não fiz nenhum commit. Executar git init já registra uma versão desses arquivos?

Conferir a explicação

Não. O git init apenas inicia o repositório. Precisamos selecionar os arquivos com git add e depois registrar uma versão com git commit.

O envio ao repositório remoto é feito com git push.

Meu laboratório

O desafio é publicar este caderno usando Git, Docker, Nginx e Jenkins, de modo que uma alteração no código chegue ao ar com um clique.

  1. Aplicação: página HTML estática no GitHub, rodando em Nginx.
  2. Servidor de CI: Jenkins em um container Docker.
  3. Jenkinsfile: as instruções do pipeline, guardadas no repositório.
  4. Integração: job Pipeline lendo o Jenkinsfile do GitHub.
  5. Teste: alterar o HTML, enviar com git push e rodar o job de novo.

O pipeline em três etapas

Checkoutbusca o código no GitHub
Buildconstrói a imagem Docker
Deploytroca o container antigo pelo novo

O Jenkinsfile fica na raiz do repositório. Por isso o GitHub é a única fonte da verdade do processo de automação.

Docker e Nginx

FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
COPY style.css /usr/share/nginx/html/style.css
COPY script.js /usr/share/nginx/html/script.js
docker build -t caderno-devops:1.0 .

Constrói a imagem da pasta atual.

docker run -d --name caderno-devops -p 127.0.0.1:8081:80 caderno-devops:1.0

Sobe o container na porta 8081.
